# Live integration tests against a real WorkAdventure

A disposable WorkAdventure stack built from the **official images** (same services and layout as
WorkAdventure's `contrib/docker/docker-compose.prod.yaml`, reduced to HTTP on `*.wa.localhost`), with
AdminSpace running from **its own production image** on the same Docker network. Scenario scripts drive a
real WorkAdventure player and the AdminSpace back office with Playwright.

Never point these scripts at a production WorkAdventure: they ban, restart and stop services.

## Prerequisites

- Docker with Compose v2, ports 80 and 4100 free on 127.0.0.1.
- A WorkAdventure checkout (its `maps/` folder is served read-only as test maps).
- AdminSpace's development PostgreSQL (`docker compose up -d db` at the repository root, port 5433).
- `npm install` and `npx playwright install chromium` at the repository root.

## Run

```sh
cd integration/live-test
./make-env.sh /path/to/workadventure                 # fresh random secrets in .env (not printed)
docker build -t adminspace:e2e ../..                 # AdminSpace production image
docker exec adminspace-db-1 psql -U adminspace -d postgres -c "create database adminspace_e2e"
docker compose --env-file .env up -d                 # WorkAdventure waits for AdminSpace's /api/capabilities

# Avatar catalog, imported from WorkAdventure's own play image (production procedure):
docker compose --env-file .env cp play:/usr/src/play/src/pusher/data ./wa-catalog
docker compose --env-file .env cp ./wa-catalog adminspace:/tmp/wa-catalog
docker compose --env-file .env exec adminspace node build/cli/seed.js --from /tmp/wa-catalog

# Test superadmin (password generated by make-env.sh):
docker compose --env-file .env exec -e ADMIN_PASSWORD="$(cat admin-password)" adminspace \
    node build/cli/create-superadmin.js --email live-admin@example.test --name "Live Test Admin"

# The scenarios create organization "live", world "office" and room "lobby" through the back office
# the first time (scenarios.mjs), using WorkAdventure's maps/starter/map.json.
node scenarios.mjs            # entry, online status, broadcast, reload, ban (live kick), re-entry, unban
node ban-reentry.mjs          # a banned identity coming back from a new tab
node settings-scenario.mjs    # a world setting: effect in WorkAdventure, persistence across restarts
node outage-scenario.mjs      # play stopped then restarted: AdminSpace reports, then recovers

docker compose --env-file .env down -v                 # remove the stack
docker exec adminspace-db-1 psql -U adminspace -d postgres -c "drop database adminspace_e2e"
```

## Known WorkAdventure issues found (commit b57916667f0f)

1. **Admin API answers cached by the pusher.** `play/src/room-api/authentication/AdminAuthenticator.ts`
   calls `setupCache(axios)` on axios's global instance, which `play/src/pusher/services/AdminApi.ts`
   also uses: GET answers (`/api/room/access`, `/api/map`...) are cached for 5 minutes by default. A
   person banned after being let in could come back from a new tab. AdminSpace now marks every Admin API
   answer `Cache-Control: no-store` (honoured by axios-cache-interceptor); regression test
   `tests/adminApi.cache.test.ts`.
2. **Admin broadcasts not displayed.** The pusher's `POST /message` (`play/src/pusher/controllers/AdminController.ts`)
   sends `type: ""`, and `GameScene.showUserMessage` only displays `type === "message"`. Messages are
   delivered but not shown. An upstream fix would send `type: "message"`.
3. **Names of guests are not sent at entry.** `/api/room/access` carries no name; the pusher only calls
   `/api/save-name` when a name is saved later. Guests appear without a name in AdminSpace (they are named
   in the live list, which comes from the pusher).
4. Configuration notes for this version: play refuses to start without `UPLOADER_URL`; the official
   `contrib/docker/docker-compose.prod.yaml` does not pass `ADMIN_SOCKETS_TOKEN` to play (needed for live
   kicks and the live list), so add it in an override.
